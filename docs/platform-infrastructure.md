# Инфраструктура MacBookBro

Актуальная схема после переноса на Timeweb 02.10.2026. Монорепозиторий: `latnikov/mac-price-radar`, ветка `dev`. Коммит установленного приложения указан в `platform-release.json`, `/var/lib/macbookbro-ops/deploy.json` и HTTPS-заголовке `X-MacBookBro-Commit`. GitHub хранит исходники; рабочие данные и секреты туда не попадают.

## Домены и приложения

Все четыре A-записи в DNS Selectel указывают на Timeweb `201.34.144.229`. Caddy принимает HTTPS, выпускает и обновляет сертификаты самостоятельно. Приложения слушают только loopback. Старый Selectel `135.106.220.39` оставлен для восстановления и временного HTTPS-прокси на Timeweb при старом DNS; его писатели, воркеры и таймеры остановлены и отключены.

| Адрес | Назначение | Каталог / служба / порт |
|---|---|---|
| `dev.macbookbro.ru` | Парсер, цены и анализ поставщиков; открыт без входа | `/srv/mac-price-radar/dev`, `mac-price-radar@dev`, 4174 |
| `macbookbro.ru` | Каталог, корзина, кабинет и заказ | `/srv/macbookbro-shop`, `macbookbro-shop`, 4190 |
| `macbookbro.ru/order/` | Прежняя форма подбора и заказа, включённая в основной домен | `/srv/macbookbro-orders`, `macbookbro-orders`, 4180 |
| `crm.macbookbro.ru` | Администраторы, чаты, контакты, сделки, МойСклад, аналитика | тот же магазин, отдельный адрес и разрешённые CRM-маршруты |
| `order.macbookbro.ru` | Постоянный 308 на `/order/` основного домена | Старые подписанные `/api/relay/claim`, `/ack`, `/status` сохранены для совместимости |

`macbookbro.ru/crm` также работает с обычной формой. Модалки HTTP Basic Auth и автоматического повышения роли через заголовок прокси нет. На CRM-домене доступен только CRM и его медиа, каталог остаётся на основном домене. `/prices/` основного домена использует ту же dev-базу, отдельный prod-парсер остановлен. Его историческая база сохранена и резервируется.

## Сервер и доступ

Timeweb AMS-1, Ubuntu 26.04.1 LTS, два vCPU, около 4 ГБ RAM, диск около 50 ГБ. Перенос клиентских данных в Амстердам явно разрешён владельцем 02.10.2026. Подключение с настроенного Mac: `ssh macbookbro` или `ssh macbookbro-timeweb`; Selectel — `ssh macbookbro-selectel`. Ключ Timeweb — `~/.ssh/mbro_timeweb`, отдельно от GitHub. SSH: только ключи, root допускается по ключу, X11 выключен, три попытки аутентификации, 30 секунд на вход. UFW разрешает TCP 22/80/443. Caddy admin API и порты приложений доступны локально. Часовой пояс сервера — Europe/Moscow.

Код установлен как единый неизменяемый релиз в `/srv/macbookbro-releases/<SHA>`: `/srv/mac-price-radar/dev` и `/srv/macbookbro-shop` указывают на корень, `/srv/macbookbro-orders` — на `order-site`. Рабочие данные парсера лежат в `/srv/macbookbro-data/parser` и подключены к релизу симлинком `data`. Базы магазина и заказов сохраняют прежние пути в `/var/lib`. Проверенный перенос сравнил SHA-256 и количества всех таблиц четырёх SQLite-баз до запуска новых писателей.

Секреты: `/etc/mac-price-radar/*.env`, `/etc/macbookbro-shop.env`, `/etc/macbookbro-orders.env`, `/etc/macbookbro-shop/*`. Не выводить их содержимое в журнал, не прикладывать к коммитам. Рабочие службы запускаются от `radar`, настройки доступны только root и необходимым службам. Резервные архивы содержат секреты и персональные данные: каталоги 0700, архивы 0600.

## Сотрудники и авторизация

Четыре учётные записи: Vlad, VladJr, Max, Sasha. Max — владелец, остальные — менеджеры. Первоначальные пароли установлены по прямому указанию владельца. В `/etc/macbookbro-shop/staff-users.json` хранятся только индивидуальные соли и scrypt-хэши; значения паролей в репозиторий не записываются. Имена регистронезависимы; пароли регистрозависимы.

Сотрудник получает сессию с личным именем для журнала действий. После входа меняются токен и CSRF. Сотрудническая сессия действует два часа и распространяется на поддомены через Secure/HttpOnly/SameSite cookie. Парсер `dev.macbookbro.ru` по просьбе владельца открыт без входа и не зависит от CRM-сессии; CRM и `/prices/` сохраняют вход сотрудника. Пользовательская корзина имеет отдельную сессию. Запросы записи проверяют Origin и CSRF; лимит входа — восемь попыток за 15 минут на IP, вычисление хэшей ограничено четырьмя параллельными операциями. Пароли, совпадающие с именами, предсказуемы: ограничения частоты не защищают от угадывания известного имени. Изменение этой политики требует решения владельца.

## Независимые процессы

| Служба | Работа | Ограничение |
|---|---|---|
| `macbookbro-shop` | HTTP магазина и CRM | MemoryHigh 192M, MemoryMax 320M, TasksMax 64 |
| `macbookbro-worker` | Цены каждую минуту, МойСклад/Авито каждые 5 минут, Telegram каждые 5 секунд, очереди, импорт старых заказов | heap 256M, MemoryMax 448M, Nice 5, перезапуск при сбое |
| `mac-price-radar@dev` | HTTP парсера | heap 256M, MemoryMax 384M |
| `mac-price-radar-collect.timer` | Почасовой сбор сайтов в единую dev-базу | CPUQuota 50%, MemoryMax 448M, таймаут 18 минут |
| `mac-price-radar-apify.timer` | Серверный сбор Авито | MemoryMax 384M; существующие паузы при ограничениях сохранены |
| `macbookbro-health.timer` | Проверка раз в минуту | После трёх неудач перезапускает активную службу; статус в CRM |
| `macbookbro-backup.timer` | Бэкап ежедневно в 02:30 MSK, случайная задержка до 5 минут; пропущенный запуск выполняется | CPUQuota 35%, MemoryMax 192M, Nice 15, таймаут 30 минут |
| `macbookbro-deploy.timer` | Проверяет GitHub dev каждые две минуты и публикует только конкретный SHA с успешным CI | Изолированные проверки от radar, блокировка одновременных выпусков, короткое переключение кода, откат без возврата старых заказов |

Встроенное почасовое обновление HTTP-парсера выключено: сбор выполняет один таймер. Старый prod-парсер и старый сломанный backup timer отключены. На Linux сбор использует kernel flock: ядро освобождает блокировку при завершении или аварии процесса. Файл build.lock не удаляется, его наличие не означает активный сбор. На Mac сохранена прежняя проверка PID. Фоновые задачи магазина не пересекаются со своим предыдущим запуском. HTTP-процесс не восстанавливает активные задания работающего воркера.

Работа служб не требует Codex, агентов, лимита модели или включённого Mac. Зарубежный источник теперь пробуется сервером напрямую вместо ожидания Chrome на Mac. При блокировке внешнего сайта предыдущий снимок сохраняется с исходной датой и явной ошибкой; это не подтверждение свежести. API МойСклад, Авито и Telegram сохраняют свои внешние ограничения: тариф Авито может запрещать историю; Telegram Business требует подключения и разрешений; Bot API не даёт историю подписок. Недоступность источника нельзя устранять придумыванием данных или повторной отправкой неоднозначного исходящего сообщения.

Уведомления новых заявок отправляет сервер через прежнего Telegram-бота. Проверенный IPv4 используется с hostname/SNI api.telegram.org и обязательной проверкой сертификата. Relay-маршруты сохранены для отката, но в прямом режиме недоступны. При переключении неотправленных клиентских уведомлений нет, установка проверяет очередь. Явное отклонение Telegram допускает повтор; потерянный ответ или прерванная отправка получает notification_state=unknown. Сначала проверить целевой чат: сообщение могло быть доставлено. Только после подтверждения отсутствия допустим ручной повтор. Монитор показывает unknown и заявки без уведомления старше часа. Приём и хранение заявки продолжаются при недоступном Telegram.

## Данные, поля и рост

SQLite используется в WAL: несколько читателей, один писатель; короткие транзакции, индексированные выборки. На production Node 24.21.0 использует SQLite 3.53.4. Python 3.12 использует SQLite 3.45.1 для проверок и резервного чтения. Новый бэкап читает каждую базу в одной транзакции и сразу сжимает SQL-представление этого снимка. [Документация WAL](https://sqlite.org/wal.html).

| База / таблицы | Какие поля храним и зачем | Очистка |
|---|---|---|
| dev `master.sqlite`: `sellers`, `sources`, `listings` | идентификаторы продавца/источника, external_id, URL, нормализованные атрибуты | Не удаляются автоматически |
| `runs`, `source_runs` | ID, время, хэш входа, статистика полноты и ошибок сбора | Сохраняются |
| `observations` | seq, ID, run/listing ID, observed/received time, rejected; JSON нормализованной конфигурации, RUB/priceMinor, stock/condition/region, validation/evidence | Сохраняется вся история цен; `raw` больше не создаётся автоматически как копия той же записи |
| `price_decisions`, `quote_revisions`, `audit`, `calculations` | версия решения/коммерческого предложения, операция, хэш, автор, причина, расчёт | Не удаляются; append-only защита сохраняется |
| shop `products`, `price_recommendations`, `catalog_imports` | ID, публикация и ревизии конфигурации, привязка цен dev и срок актуальности | Обновляются по бизнес-правилам, старые заказы независимы |
| `orders`, `order_customers`, `fulfillment`, `order_proposals`, `costs` | принятый снимок товара и цены, доставка и согласования, себестоимость отдельно | Не удаляются и не переоцениваются при изменении каталога |
| `legacy_order_sources` | исходный ID MB-XXXXXXXX, неизменённый payload и его хэш | Импорт повторяем; изменение принятого источника вызывает ошибку, исходящие задания не создаются |
| `customers`, `crm_profiles`, `deals`, `deal_events`, `tasks`, `crm_merges` | контакты, классификация, примечания, стадия, ответственный, сроки, история | Не удаляются |
| `inbox_accounts`, `inbox_dialogs`, `inbox_messages` | account/channel/remote ID, время, направление, текст, статус прочтения, признаки полноты | Переписка сохраняется; одна запись на пару аккаунт/remote ID, список и история индексированы и пагинируются |
| `ms_objects`, `sync_state` | исходный JSON объектов МойСклад, курсоры и состояние синхронизации | JSON пока сохраняется для совместимости и аудита |
| `ms_document_facts` | type/remote ID, counterparty ID, currency ID, сумма в копейках, проведённость, moment, name | Индексированная проекция продаж и возвратов; карточка клиента не перебирает все финансовые JSON |
| `jobs`, `publications`, `inbox_outbox`, `customer_outbox` | идемпотентность, ревизия, очередь, результат и неоднозначность отправки | Незавершённые/неоднозначные задачи не удаляются |
| `sessions`, `staff_sessions`, `account_sessions`, `limits`, `checkouts`, `account_tokens`, `signed_nonces` | токены только в виде хэшей, CSRF, роли/имя, корзина, сроки, счётчики | Каждый час: истёкшие сессии/лимиты и непринятые checkout; истёкшие nonce; токены спустя сутки после срока |
| `telegram_update_queue`, версии сообщений/подключений | durable событие, offset, повторы, права, tombstone | Только обработанные/игнорированные payload старше 7 дней; ожидающие события и защита версий остаются |
| orders `orders.sqlite` | четыре прежних клиентских заказа, служебная relay-проверка, новые из `/order/`, idempotency и notification_state | Клиентские заявки копируются в CRM без повторных уведомлений; MB-RELAY-TEST остаётся только в исходной базе |

До оптимизации наблюдение цен занимало в среднем 4,2 КБ, из них около 1,8 КБ составлял повторный `raw`. Историческое сжатие снимает только `raw`, чьи ключи и типизированные значения уже дословно совпадают с верхним уровнем. Отличающиеся исходные сведения остаются. `VACUUM` возвращает свободные страницы файловой системе. Процедура выполняется при остановленных писателях, после свежего проверенного бэкапа; проверяет количества всех бизнес-таблиц, quick_check и FK. Она не сокращает срок хранения цен и не удаляет ценовые наблюдения.

JSON не запрещён повсеместно: неизменяемое согласованное предложение удобно хранить целиком. Поля, по которым идут массовые фильтрация/поиск/суммирование, должны иметь колонки и индексы. Нельзя без проверки потребителей удалить произвольные поля source JSON. Медиа не следует хранить в SQL BLOB; сейчас это отдельный файловый каталог. Следующий шаг при росте вложений — S3 с квотами и лимитами размера, а не расширение JSON в переписке.

Ранние заявки без configurationDescription показывают исходные поля конфигурации. Их неизвестная прежняя цена остаётся неизвестной. `/order/` сохраняет предварительные расчёты прежнего конфигуратора и их исходную дату; его цены не подменяются текущими рекомендованными ценами MacBook. Общая CRM принимает обе формы заказа, но полная унификация ценового движка конфигуратора требует отдельных подтверждённых данных Mini/Studio/Pixel.

## Производительность

Публичный каталог отдаётся готовым HTML без обязательного JavaScript, шрифтов и сторонних библиотек. Анонимный просмотр не создаёт сессию в SQLite. Ограниченный кэш на 100 вариантов живёт до 5 секунд, сбрасывается при изменении базы другим процессом и не переживает срок цены; ETag позволяет 304. Caddy сжимает ответы. Персональные формы, корзина и CRM не кэшируются публично. Индексы ускоряют документы клиента, историю диалогов и очистку истёкших объектов.

Точные замеры, объёмы баз, состояние интеграций и прогноз — в `platform-audit-2026-10-01.md`. Срок, на который хватит сервера, зависит от числа наблюдений в день и вложений. Монитор предупреждает при диске >80%, доступной RAM <200 МБ, старом бэкапе, ценах и интеграциях. Увеличивать до 2 vCPU/4 ГБ следует при длительном CPU >70%, доступной RAM <300 МБ или заметном росте p95/ошибок при обычной нагрузке. PostgreSQL оправдан при измеренной конкуренции писателей и необходимости нескольких серверов; один небольшой сервер и четыре менеджера не требуют этого автоматически.

## Бэкапы и восстановление

Конфигурация: `/etc/macbookbro-platform.json`. Инструменты без сторонних зависимостей: `/usr/local/lib/macbookbro-ops/{maintenance,audit,compact}.py`. Состояние: `/var/lib/macbookbro-ops/`; монитор читается CRM на `/crm/system`.

Ежедневный архив `/var/backups/macbookbro-platform/platform-*.tar.gz` включает четыре согласованных SQLite snapshot, код приложений, серверные настройки/секреты, состояния источников и медиа. Формат 2 содержит `*.sqlite.sql.gz`: данные сжимаются при чтении, промежуточных полных SQLite-копий нет. Schema, индексы, триггеры, AUTOINCREMENT, user_version, application_id и page_size сохраняются; generated columns пересчитываются из исходных значений. Unicode, переводы строк, кавычки, NUL и BLOB восстанавливаются без обрезания. Для каждой базы quick_check, FK и количества **всех** пользовательских таблиц проверяются внутри той же транзакции чтения. SHA-256 всех файлов проверяется после сжатия до публикации архива. Старый бинарный формат 1 остаётся поддержанным. Восстановление потоковое, в одну транзакцию на базу, без загрузки полного SQL в RAM; результат — отдельный SQLite-файл без зависимости от WAL исходника.

При нехватке места архивирование останавливается с явной ошибкой, исходники не удаляются. До запуска проверяется запас на два размера последнего архива плюс 768 МБ; во время экспорта сохраняется резерв 256 МБ. Это оценка для создания копии, а не гарантия при резком росте вложений. Лимит хранения — семь поколений или 3 ГБ, но минимум две проверенные копии всегда сохраняются: если две копии сами превысят лимит, их не удаляют ради формальной квоты. Полная проверка восстановления выполняется отдельно и требует места под восстановленные базы плюс распакованный архив. Ежедневная отметка verified означает проверки исходного снимка и целостности архива; последняя успешная полная проверка записана в restore-check.json. Копии успешных новых установок маркируются, сжимаются и удерживаются в количестве трёх или 512 МБ с минимумом двух. Старые немаркированные ручные копии не трогаются этой ротацией.

Журналы ограничены 128 МБ на диске / 32 МБ runtime и семью днями. Очистка не запускает тяжёлый VACUUM на рабочей базе магазина.

Разовое сжатие истории запускается явно: `systemctl start macbookbro-compact.service`, после свежего проверенного бэкапа. Служба останавливает писателей парсера и возвращает dev и таймеры в конце. Изменение представления и восстановление append-only триггера фиксируются одной транзакцией на пакет; прерывание не оставляет таблицу без защиты. Магазин и CRM продолжают работать, источник цен на время недоступен, исходные сроки цен сохраняются.

Проверить службы и получить отчёт:

```sh
systemctl is-active macbookbro-shop macbookbro-worker macbookbro-orders mac-price-radar@dev caddy
systemctl list-timers --all
python3 /usr/local/lib/macbookbro-ops/audit.py
journalctl -u macbookbro-worker -u macbookbro-backup -u macbookbro-health -n 60 --no-pager
```

Сделать свежую копию и проверить восстановление в **пустом** каталоге:

```sh
systemctl start macbookbro-backup.service
cat /var/lib/macbookbro-ops/backup.json
python3 /usr/local/lib/macbookbro-ops/maintenance.py verify --archive /var/backups/macbookbro-platform/platform-TIMESTAMP.tar.gz --destination /var/backups/macbookbro-restore-check
```

Verify не заменяет рабочую базу. Для аварийного восстановления: остановить службы, сделать отдельную копию нынешних файлов, выбрать проверенный архив, выполнить verify, установить нужные SQLite в исходные пути (перечислены в `/etc/macbookbro-platform.json`) и восстановить владельца radar/права 0600, удалить только sidecar старой остановленной базы, восстановить подходящую версию кода и конфигурации, запустить службы и проверить заказ/карточку клиента. Между четырьмя базами snapshot берутся последовательно: это не общая транзакция, повторяемый импорт заказов согласует их после восстановления.

Копия вне сервера обязательна для защиты от потери самого диска. Исторический архив уже вынесен на Mac; автоматического S3-получателя без предоставленного хранилища нет. До настройки S3 ежедневные архивы локальные. Внешнее оповещение также требует указанного канала: сейчас изменения состояния записываются в журнал и видны в CRM. `alert_command` можно задать в закрытой серверной конфигурации для явного адресата, отправка клиентам не предусмотрена.

## Проверки и публикация

`npm test`, `npm run test:orders`, `npm run test:shop`, `npm run typecheck`, `python3 -m unittest discover -s deploy/platform -p 'test_*.py'`. CI запускает эти проверки при push dev/main и PR. Есть тесты принятых цен/заказов, идемпотентности, ошибочных источников, CSRF/ролей/входа, переписки и её версий, учёта валют/возвратов, восстановления/ротации/сжатия и `/order/`. Число тестов и измеряемое покрытие — в аудите; наличие тестов не означает 100% проверки всех внешних API.

Публикация на Timeweb: `git push origin dev`, затем дождаться успешного CI и `macbookbro-deploy.timer`. Сервер получает код из GitHub, проверяет его без рабочих данных, делает согласованные онлайн-снимки баз и переключает приложения на единый релиз. Неудача возвращает прежний код и сохраняет текущие базы. Ручной запуск того же процесса: `systemctl start macbookbro-deploy.service`. После публикации проверить полный SHA, публичные HTTPS-страницы, вход CRM и расчёт заказа. Подробности, ограничения отката и расположение снимков — [Timeweb deployment](../deploy/timeweb/README.md). Прежний `deploy/platform/install.py` сохранён для старой схемы Selectel и не используется таймером Timeweb.

Изменения приложения проходят полный цикл «залей»: тесты → коммит → push → установка → проверка опубликованной версии. Доступ и процедуры описаны здесь, чтобы любой следующий инженер мог подключиться по SSH и работать без этой беседы.
